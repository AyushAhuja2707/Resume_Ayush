fig. 01 — dual-queue OTP
CASE 01 · AUTHENTICATION

Dual-queue OTP handling for HDFC Netbanking

OTPs on HDFC NetBanking were taking 4–5 minutes to arrive at peak, because generation and verification fought over the same pipeline. I split the work into two independently drained queues and added token caching, so neither path could starve the other.

4–5 min → <1 minOTP delivery, 70% faster, held at peak volume
Java 17Spring BootConcurrencyQueues
Read the notes
ProblemA single shared path for OTP work meant contention spikes translated directly into user-visible login delays.
ApproachSeparate queues with their own consumers, so throughput scales per path and back-pressure on one doesn't block the other.
ResultOTP delivery went from 4–5 minutes to under a minute (70% faster) and held under peak transaction volume, with no new infrastructure.
fig. 02 — JVM token cache
CASE 02 · INTEGRATION

JWT integration with CCIL, without the chatter

Every outbound CCIL call was re-authenticating. I designed a 24-hour JVM-level token strategy with expiry tracking and automatic refresh, so services share one valid token instead of minting their own.

1 tokenper 24h window, instead of one per call
JWTCachingRESTSecurity
Read the notes
ProblemRedundant authentication calls added latency and load on both sides of the integration.
ApproachAn in-JVM token cache with expiry handling and refresh logic that stays inside CCIL's security and compliance requirements.
ResultFewer API calls, higher throughput, and simpler resource usage.

fig. 05 — strict-reference generation
CASE 05 · AI-ASSISTED ENGINEERING

Prompts that write the code, the tests and the error lists

I prepared a strict-reference prompt for our banking API work. It generates implementations only from approved sources such as API contracts, field mappings and existing behaviour. When a reference is missing, it stops and names the gap instead of guessing a business rule. A second prompt takes any API and gives back its complete error list, so the bank can trace and fix issues quickly.

Code + testsmost of the development work, including test cases, generated from the prompt
Prompt engineeringAI agentsTest generationError cataloguesJavaDSALLDSystem design
Read the notes
ProblemGenerated code can look right while quietly inventing a business rule, which is unacceptable in banking.
ApproachFind the approved sources, generate only within them, halt with a named gap for an owner when evidence is missing or conflicting, then review against the cited sources.
TestsThe same prompt produced test cases from those references, so the code and its checks trace back to the same evidence.
Error listsGive the LLM an API and the prompt returns that API's error list: the error codes, what triggers each one and how to resolve it. Already run across many APIs, it gives support teams and the bank a ready reference for solving issues fast.
ResultMost of the development work ran through the framework, with engineers keeping the final review and peer-review gates.
